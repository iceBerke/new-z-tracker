# Gotchas — real bugs we have already hit

Every entry is a failure that reached working code, together with the reasoning that explains why
the fix is shaped the way it is. **The why is the value.** These are long on purpose: the cost
they prevent is someone re-deriving a decision from scratch and getting it wrong.

`CLAUDE.md` carries a one-line index that routes here **by trigger** — what you would be doing
when an entry becomes relevant. Read the index first and come here when a line matches your task.

**Entries are appended and extended, never rewritten.** When something new is learned about an
area that already has an entry, add to it. An entry quietly kept current stops being evidence of
what actually happened — the same rule `docs/CHANGELOG.md` states for its rows.

A few entries record a **costed decision** rather than a bug that was hit; each says so in italics
under its heading. They live here because the trigger is the same code you would be editing. The
genuinely *open* items — deferred and still undone — are in `docs/DECISIONS.md` instead.

## Build, deploy & repo hygiene

*Running the build, deploying to Fiji, or editing a file in this repo.*

### Counting tests and updating the changelog row after a patch

- **Test counts must come from a clean run, and the changelog row must be checked as actually edited — not assumed from having computed it.** (That row lives in `docs/CHANGELOG.md` since p10.18; it was in README before that, which is what the story below refers to.) Every patch row carries a count, so this recurs on every patch. Summing `target/surefire-reports/*.xml` is **not** a reliable source: that directory retains reports from any class run since the last `clean`, including throwaway dump/probe classes, so the sum silently overcounts. Take the count from `mvn clean test` (or the `Tests run:` total of a `mvn clean install`). **Since p10.14 that run prints _two_ `Tests run:` totals and the count is their sum** — `default-test` (**254**) plus `streaming-invariant-test` (**1**) = **255**. Do not read the first total as the whole suite. The split is not cosmetic: the second execution exists only so `ProjectionStackScannerMemoryTest` can run forked under `-Xmx96m`, and **that cap is the entire assertion** — surefire cannot vary `-Xmx` per class within one execution, and without the cap the test asserts nothing, since a load-all-then-project refactor produces identical numbers. If a future patch collapses the two executions back into one, it has silently deleted the guard, not tidied the build. This has already gone wrong once: a stale dump-class report inflated 226 to 227, the wrong number reached the README, and it was then reported as fixed when the edit had only been computed, never made. So: clean run for the number, and `grep` the README row to confirm the edit landed before committing.

### Editing a repo file from PowerShell

- **Never round-trip a repo file through PowerShell `Set-Content` — it silently re-encodes UTF-8 to CP1252 and corrupts every em-dash in the file, including ones you did not touch.** Hit for real while editing `pom.xml` during p10.14: reading the file with `Get-Content -Raw`, changing one string, and writing it back with `Set-Content -Encoding utf8` turned every `—` into `â€"` — **throughout the whole file**, not just the edited line, because the corruption happens on the read/write round-trip rather than at the edit. **It is invisible in normal output**: the build still succeeds, `mvn test` still passes, and the mojibake only shows up if you grep for it or read the diff closely. This repo's prose is full of em-dashes — `CLAUDE.md` and `README.md` especially — so a single careless round-trip can rewrite hundreds of lines and bury the real change. **The rule: edit files with the Edit/Write tools, never via `Get-Content`/`Set-Content` (or `Out-File`, or `>`).** If it has already happened, do not hand-patch the characters — `git checkout -- <file>` and re-apply the edit properly, which is what p10.14 did. Two ways to catch it: grep the changed files for `â€`/`Ã`/a `ï»¿` BOM, and check `git diff --stat` for a suspiciously large line count on a file you barely edited (a re-encode shows up as every em-dash line rewritten). **The corrupted example spelled out above is deliberate, so a repo-wide mojibake sweep will always report exactly one hit — this line — which is not corruption and should not be "fixed".** **A second, quieter hazard in the same family: `Set-Content -Encoding UTF8` writes UTF-8 *with a BOM* on Windows PowerShell 5.1.** It does not corrupt a single character, so the mojibake sweep passes and the file reads correctly everywhere — but three `EF BB BF` bytes now sit at the front, and nothing in normal output shows them. Hit on **all three** files written while splitting this file out of `CLAUDE.md`; each had to be stripped afterwards. **The rule for generated files: write with `[System.IO.File]::WriteAllText(path, text, (New-Object System.Text.UTF8Encoding($false)))`** — the `$false` is the no-BOM flag — and check the first bytes rather than trusting that correct-looking text means a correct file. (Note if a generation script is ever blocked as *"This script contains malicious content"*: that is an **antivirus/AMSI heuristic false positive** on the shape of the script — loops plus reflection reads as obfuscation — not a defect in it. Simplify the script or split it; do not conclude the approach was wrong.)

### Running mvn install with Fiji open

- **A running Fiji locks the JARs in its plugins folder, so `mvn install` could report success while leaving the previous version behind — a silently double-registered plugin.** Hit for real while deploying p10.8 with Fiji open: `clean-old-jars` logged `[delete] Deleting …z-tracker-v4-p10.7.jar`, `verify-deploy` echoed `OK`, `BUILD SUCCESS` — and `p10.7.jar` was still there, because Windows refuses to delete a file a live process holds open and `failonerror="false"` swallowed it. Two JARs in `plugins/` make Fiji register **all three tools twice**. Two traps here, both worth remembering: Ant's `[delete] Deleting <file>` line is its *intent*, printed before the attempt, so it is never evidence of deletion; and `verify-deploy` used to check only that the **current** JAR exists, which is a different claim from the old one being gone — a passing deploy check proved nothing about leftovers. Fixed in p10.8 by a third `verify-deploy` assertion (`pathconvert` with `setonempty="false"` over `z-tracker-v4-*.jar` excluding the current version, then `<fail if="stale.jars">`) that fails the build naming every leftover. **Keep `failonerror="false"` on the delete** — it lets the sweep finish across the other files — and keep the enforcement in `verify-deploy` rather than moving it into the delete. The specific case this catches is a **version bump with Fiji open**: the *new* filename doesn't exist yet so `copy-to-fiji` succeeds, while the *old* locked one fails to delete — deleting silently. (When the current version's own JAR is locked, `copy-to-fiji` fails first with a plain Maven `FileSystemException`, so that case was never silent.)

### Indexing a PowerShell hashtable whose key is also a member name

- **`$h.count` on a PowerShell Hashtable returns the entry count, not the `'count'` key — and the failure surfaces far from its cause.** Hit for real while generating this very file: a lookup table `$G = @{ count='Counting tests…'; fiji='…' }` was read as `$G.count` to build a link, and **PowerShell resolves real object members before dictionary keys**, so `$G.count` returned the `Hashtable.Count` **property** — the number of entries, `15`, as an `Int32` — rather than the string under the `'count'` key. The same collision applies to **`Keys`, `Values`, `Length`** and every other member name. **The symptom was not a wrong value, which would have been obvious, but a downstream type error:** the `Int32` was passed to a slug helper that called `.ToLower()`, which threw `[System.Int32] does not contain a method named 'ToLower'` — an error naming a function several lines away from the actual mistake, with the offending expression nowhere in the message. Nine of those scrolled past while the replacement text they were building silently collapsed, truncating gotcha bodies mid-sentence to a bare `see [` and **deleting the text that followed**. **The rule: index a hashtable with `$h['count']`, never `$h.count`, whenever a key could collide with a member name** — and prefer `['…']` unconditionally in generated-text code, where a wrong lookup corrupts output rather than crashing. **On the truncation specifically: the likely mechanism is that the nested `@( @('old','new'), … )` replacement-pair array flattened when the `'new'` expression yielded an unexpected number of objects, so `$r[1]` picked up only the first fragment. That is *inference* from the observed output, not established fact — it was never instrumented, so do not treat it as proven.** **The structural fix was scaffold-then-substitute:** author all new prose with an editor, leave `@@BULLET_n@@` tokens where verbatim text belongs, then substitute each token for its exact source line — no concatenation of computed fragments anywhere near the content. **But the actual safeguard is the post-check, not the method.** The first attempt was careful too, and still corrupted the file, because it only verified that the old positional phrases were *gone* — never that the result *equalled the source*. The rewrite asserts, per bullet, that the text in this file is byte-identical to its line in `CLAUDE.md`. Verify equality with the source; absence of the thing you replaced proves nothing. Note this is a **second, distinct** PowerShell hazard, unrelated to the `Set-Content` encoding trap in [Editing a repo file from PowerShell](#editing-a-repo-file-from-powershell) — that one corrupts characters, this one deletes text.

### Deciding whether executable content changed

- **A hash comparison cannot answer "did the JAR's executable content change?" — it always says yes, at two independent levels.** The patch workflow makes `<patch.version>` depend on exactly that question, and hashing the artifact is the obvious mechanical check. It is the wrong one. **JAR level:** every rebuild produces a different JAR from identical source, because Maven stamps each ZIP entry with the moment it was written and this project does not set `project.build.outputTimestamp` (confirmed absent from both `pom.xml` and the effective POM). **Demonstrated, not reasoned:** two consecutive `mvn clean package` runs with `git status` clean over `src` and `pom.xml` produced JARs of **identical size, 146,578 bytes, and different SHA-256** — while all **56** `ztracker` class files inside them were **byte-identical**, isolating the difference to container metadata. **Class level:** even the class files can differ without the code changing, which [Reading pixels straight from a processor backing array](#reading-pixels-straight-from-a-processor-backing-array)'s neighbouring case at p10.17 established — a javadoc block growing by four lines shifted every `LineNumberTable` entry, so the class file was not byte-identical while `javap -c -p` output matched line for line. **The consequence is the thing the rules exist to prevent:** a hash check reports "changed" on every patch, so anyone trusting it bumps `<patch.version>` every time — which is precisely the practice retired at p10.21, where a memory rule claiming every `mvn install` requires a version bump was found contradicted by six consecutive approved documentation patches. **The correct check is to compare disassembled instructions, not bytes:** `javap -c -p -cp "target/classes;<ij-jar>" <fully.qualified.Class>` for each affected class, diffing the output. That is what p10.17 did. Verified deterministic — two runs over the same class gave identical output (426 lines), and the output contains no timestamp and no absolute path, so nothing in it varies between builds; only `LineNumberTable` entries would move, and `-c -p` does not print them. **The two levels are not equally fixable, and that asymmetry matters:** the JAR-level half is **incidental** — setting `project.build.outputTimestamp` would make the build reproducible and JAR hashes meaningful, and that is recorded as an item in `docs/BACKLOG.md` — while the class-level half is **inherent**, since debug line numbers legitimately move when comments move, and no build setting removes that. Fixing the first would still leave the second, so the instruction-level check remains the answer either way.

### Verifying a claim with a shell pipeline or a text comparison

- **A check that never ran, and a check that compared the wrong thing, both report *clean* — and clean is the answer you were hoping for, which is why neither gets a second look.** Two incidents in the p10.29 review, different mechanisms, one failure mode: **the check reported a result without having performed the comparison it claimed.** (1) **`strings <file> | grep -c -i <term>` returned `0`, reported as evidence the term was absent.** `strings` is not installed in this environment; it failed, `grep` read an empty stream, and printed `0`. **`0` from "did not run" is byte-identical to `0` from "ran and found nothing".** The shell makes this easy to miss: a pipeline's exit status is its *last* command's, so `grep` succeeding masks the failure upstream — `set -o pipefail`, or checking each stage, is what distinguishes them. Better still, prefer a tool that **errors loudly on absence** over one that returns a count: the same review re-ran a PDF scan under `pdftotext` whose output failed to decode as UTF-8, and *because the reader raised an exception rather than counting zero*, the wrong encoding was caught instead of being reported as a clean file. (2) **A line-level old-vs-new comparison used set membership where it needed a multiset intersection.** Testing `line in set(old_lines)` counts a line as unchanged however many times it appears, so four new callout delimiters (`:::note`, `:::`) each matched a *single* old occurrence and inflated a "byte-identical" claim by four lines. Use `collections.Counter(old) & Counter(new)` — a true 1:1 pairing — whenever the answer is a **count** rather than a yes/no, and **print both totals**, not just the intersection: the error was invisible because only the new-side total was shown, leaving the old side to be inferred, and the inference was wrong. **The general rule, since the patch workflow demands this kind of check constantly:** a verification must be able to **fail**. If every outcome of a command is a number and none of them is an error, it is not a verification — it is a number. Make the tool throw, check every exit status, and state both sides of any comparison so the arithmetic can be checked by whoever reads the report. Both of these were caught in review rather than shipped, but only because someone re-derived the arithmetic by hand.

- **Four more of the same, from the p11.6 and p11.7 reviews — all caught, none shipped, and every one either reported *clean* or reported a number that came from somewhere else.** *(Appended p11.8; incidents (1) and (2) above are p10.29's.)* **(3) An `&&` chain short-circuited on a grep that found nothing, so the command after it never ran.** `git diff … | grep -i "pipeline" && node docs/build-guide.mjs; echo "node exit=$?"` printed **`node exit=1`** — which was the **grep's** status, not node's: `&&` skipped node entirely, and `$?` reports the last command that actually executed. The regeneration silently did not happen, and the line reporting it read like a node failure. Put `;` between independent steps, or check by name the status of the step you actually care about. **(4) A diff filter that silently dropped every markdown list line.** `git diff | grep -E "^[-+][^-+]"` is the usual idiom for "changed lines, not the `+++`/`---` headers" — but a changed **list item** reads as `+-` or `--`, which `[^-+]` excludes. It reported **3** changed lines where there were **5**, hiding two of the lines under review. Match `^[-+]` and exclude `^(\+\+\+|---)` explicitly instead. **(5) `git grep` missed a claim that wrapped across a line break and returned exit 1**, which reads as "not present". `README.md` held *"are exactly / what step 2 reads as input"* split over two lines, and the nil result was nearly taken as evidence the claim had already gone. **Prose in this repo is hard-wrapped, so any multi-word claim can be invisible to a line-based search** — read the surrounding lines before trusting a nil, which is how this one was actually found. **(6) `javap` exits 1 and writes nothing when it cannot resolve a class**, which is indistinguishable from clean output — and a diff of two empty files passes. The cause was a MinGW-style path inside a `;`-joined classpath, `javap -cp "/tmp/base_classes;$CP"`: Git Bash rewrites a lone path argument but never one embedded in a longer string, so the **Windows** JDK received a path it could not read. `cygpath -w` fixes it. Because `<patch.version>` decisions rest on this output, **check exit status *and* line count on both sides before comparing** — the p11.7 check reported `exit=0` and `402`/`712` lines explicitly for exactly that reason.

## Dialogs & frame alignment

*Touching any AWT dialog, or the CSV-to-TIFF frame offset.*

### Styling a freshly constructed AWT Label

- **AWT Label.getFont() returns null before peer creation.** Calling `getFont().deriveFont(...)` on a freshly constructed `Label` that hasn't been added to a visible container will NPE. Always null-check and fall back to `new Font(Font.DIALOG, Font.PLAIN, 12)` before deriving a style.

### Setting the CSV-to-TIFF frame offset

- **Frame indexing mismatch.** Tracking CSVs are often 0-indexed while TIFF files start at frame 1. `FrameAligner` handles a configurable offset; the most common correct value is **+1**. **Always preserve the offset confirmation/preview step** in the dialog — silent misalignment corrupts results. The offset *suggestion* is start-anchored (`suggestOffset` = firstTiff − minCsvFrame) and is only a hint — the user confirms. The offset is a single constant applied to every detection, so the correctness test is per-frame: does `frame + offset` land on an existing TIFF for every detection (`missingFrameCount`)? **Do NOT infer a bad offset from the CSV frame range being shorter than the TIFF range** — a track that covers only part of the recording is normal (a cell appears then vanishes), so an end-anchored `lastTiff − maxCsvFrame` heuristic false-alarms and was removed. Instead, `validate` reports alignment **per track** (`AlignmentReport.perTrack`: each track's frame span, detection count, and how many detections map to a missing TIFF). The step-4 UI is a single custom AWT dialog that **live-updates** as the user edits the offset: the compact in-box verdict comes from `perTrackAlignment` + `buildBoxSummary`. So the user can **verify before confirming**, the full per-track table (capped at 50 rows — each track's span plus how its first/last frame maps) is written to the Fiji log via `validate` **once per distinct offset actually evaluated** (deduped against the last-logged offset, so keystrokes within one number don't re-dump), starting with the suggested offset when the box opens; on confirm it logs the table again under a `CONFIRMED` header. The confirm checkbox default tracks `all tracks fully mapped`. The dialog is **modeless** (blocks the plugin thread with a `CountDownLatch`, not by AWT modality) so the Log window stays interactive/resizable while it is open. Per-track rows are ordered by **track id** — numerically when the ids parse as integers (so `10` sorts after `2`, not lexicographically before it), otherwise lexicographically.

## Tool 1 — streaming & pixel reads

*Editing how the projector reads slices or folds them into a projection.*

### Refactoring how the TIFF-stack input reads slices

- **Tool 1's TIFF-stack input must stay streaming — do not "simplify" it into load-all-then-project.** `ProjectionStackScanner.projectTimepoint` deliberately reads slices one at a time from a virtual stack into `ZProjector.Accumulator` instead of building a `List<float[][]>` and calling `ZProjector.project`. That is not stylistic: one real timepoint is a 401-slice 1051×1674 stack (~700 MB on disk, ~2.8 GB as floats), and the streaming form runs it in ~2 s inside a **512 MB** heap. **512 MB is the constraint the design targets, not the heap it runs in** — the deployed Fiji is given far more (24 GB on the development machine), which is exactly why a regression here would not announce itself. **The invariant holds regardless of how much heap is available**, because streaming makes peak memory a function of `w × h × (12 + bytes-per-pixel)` rather than of stack *depth*, so the plugin never approaches the ceiling at all; load-all scales with depth and would meet it on a smaller machine, a deeper acquisition, or a Fiji already holding other images. And do not assume Fiji would say so clearly when it does: the JVM can thrash for a long time before failing, and the failure can surface at an unrelated allocation, so the symptom is more likely a hang or a confusing error somewhere else than a message naming this code. The folder input type keeps the load-then-`project` path precisely because its timepoints are assembled from separate small files. **Note what that costs, which was documented nowhere before p10.16:** the folder path holds every layer at once — `w × h × 4 × layers`, plus ~8 bytes/px for the result — which is **~2.63 GiB** for that same 1051×1674×401 acquisition, i.e. precisely the profile the stack path exists to avoid. It is unavoidable there: each Z layer is its own single-image file, so there is no multi-slice file to read a piece at a time and the layers must be assembled before they can be compared. The files being small is a statement about I/O, not about peak memory. Related traps in the same method: slices are folded in **ascending-Z** order (not file order) so ties resolve to the lowest Z exactly as the folder layout does — reordering that silently changes which depth a flat/saturated region reports; and the single reused `float[][]` buffer is only safe because `Accumulator.add` **copies** (covered by `accumulator_copiesEachSlice_soCallersCanReuseOneBuffer`). **Since p10.14 this is asserted, not merely documented** — `ztracker.io.projector.ProjectionStackScannerMemoryTest` generates a 1024×1024×100 8-bit stack into a `@TempDir` at test time and projects it **forked under `-Xmx96m`** (its own `streaming-invariant-test` surefire execution; see [Counting tests and updating the changelog row after a patch](#counting-tests-and-updating-the-changelog-row-after-a-patch)). The margins: load-all would need 1024·1024·100·4 B = **400 MiB, 4.17× the cap** — measured, it dies after 22 of the 100 slices — while streaming needs 1024·1024·13 B = **13 MiB, 13.5% of the cap**, so only the streaming design can pass. (**13, not 12** — the three arrays the plugin allocates are 4+4+4, but the source slice's `ImageProcessor` is live alongside them, adding one byte per pixel for this 8-bit fixture. Do not "correct" it back by counting only the plugin's own arrays.) **The cap has to be artificial precisely because the deployment cannot detect this**: ~2.8 GB fits comfortably in the heap Fiji is actually given, so a load-all regression there would show up as mild slowness rather than a crash — invisible on the development machine and easily mistaken for normal variation. So 96 MB being far below anything real is the point, not an oversight; do not read it as excessive and raise it. It asserts **completion with a correct result**, never an expected `OutOfMemoryError` (a JVM can thrash a long time before throwing, which would make it slow and flaky), and correctness is checked per pixel against a closed-form rule — `value(x,y,k) = ((x+y+k) mod 100) + 1`, whose values at a pixel are a permutation of 1…100, so the max is unique and the expected z-origin index is unambiguous — plus one planted 255 marker. **That check must stay allocation-free** (no expected `float[][][]`): materialising the expectation would need the same 400 MiB the test forbids. Three ways to break it without touching `projectTimepoint`: raising the `-Xmx96m`, folding the class back into the main execution, or letting the fixture stop being written slice-on-demand — it is generated through a `VirtualStack` subclass because a normal in-memory `ImageStack` would need 100 MiB and OOM before the invariant ran, which is why the test asserts `imp.getStack().isVirtual()` before saving rather than leaving a bare OOM to be misread as the invariant breaking. **It also needs ~100 MiB of free temp space** (measured peak 104,873,979 B, removed by JUnit's own `@TempDir` teardown — verified once at p10.14, not asserted, since that is framework behaviour rather than anything about this plugin), so a constrained CI tmpfs is a plausible way for it to fail confusingly. Runtime ~1.3 s. **One limitation worth stating so nobody reads this test as proving more than it does:** the fixture's slice labels ascend with file order, so a layer's position in the file and its global z-index coincide — this test therefore does **not** exercise `projectTimepoint`'s ascending-Z sort, which `ProjectionStackScannerTest` covers with slices deliberately stored out of order.

### Reading pixels straight from a processor backing array

- **Reading pixels straight from the backing array needs unsigned masking — `byte`/`short` are signed in Java.** `ProjectionStackScanner.readInto` bypasses `ImageProcessor.getf` for speed (a deep stack is hundreds of millions of pixel reads) by going to the `byte[]`/`short[]`/`float[]` directly, which means intensity 200 in an 8-bit image arrives as `-56` and 40000 in a 16-bit image arrives negative unless masked with `& 0xff` / `& 0xffff`. Both are regression-tested (`projectTimepoint_reads8BitValuesUnsigned_notSignExtended`, `..._reads16BitValuesUnsigned_...`). `getf` — what the folder input type uses — already does this masking internally, which is why that path never had to think about it.

### Projecting float input that may contain NaN

- **A `NaN` never wins the projection — and the guard is on the *comparison*, not the seed, because `Accumulator` cannot look ahead.** Every comparison against `NaN` is false in Java, so before p10.11 `ZProjector.project` seeding `best` from slice 0 meant a `NaN` there **could never be beaten**: the pixel reported layer index 0 whatever the real data below it. That index is a **valid mapping key** (the lowest-Z layer), so `TiffStackLoader` loaded it, `ZMappingLoader` resolved it to a real depth, and Tool 2 reported `STATUS_OK` — a confident wrong Z, the same worst-in-the-pipeline failure class as p10.1's zero-fill. Fixed by one line, `Float.isNaN(best) ? !Float.isNaN(v) : (max ? v > best : v < best)`, in **both** `project` and `Accumulator.add`. **Three things to keep:** (1) the two lines must stay **identical** — the `Accumulator ≡ project` equivalence rests on both taking the same rule; (2) guard the comparison, **not** the seed — seeding from the first non-NaN is expressible in `project` but *not* in `Accumulator`, which is streaming and cannot look ahead, so it is the only rule both paths can share; (3) it is **inert on NaN-free input** (`best` is then never NaN, so it collapses to the original comparison) — verified over 8,000 randomised NaN-free stacks × both paths × both modes with zero divergence, and every pre-existing test passed unchanged. **Why `ZProjector` and not the two scanners:** this is a property of the *projection algorithm*, not of either input layout — both types funnel through here — so it is the same reasoning that put the cross-timepoint checks in `processDataset`, and **not** a violation of the p10.5/p10.6 write-each-check-per-input-type rule, which governs within-timepoint *input validation inside the scanners*. Duplicating it into both scanners would be the drift-prone option. Only 32-bit float input can carry NaN at all (8-/16-bit cannot represent it); the realistic producer is Fiji's **`Process > Math > NaN Background`**, a stock menu item that NaNs sub-threshold pixels of a 32-bit image — unhelpfully well-aimed, since it NaNs exactly the background where the lowest-Z layer is likely empty. **`numpy` gives the same wrong answer** (`np.argmax([nan,500,900])` → 0, `np.max` → `nan`), so the Python scripts these tools port always behaved this way and *matching the reference implementation was never a correctness argument here*. Note the port already diverged from numpy in its favour for a NaN in a *later* slice (numpy returns that slice's index; this returns the real extremum's). **The documented limit:** an **all-NaN** pixel still reports layer 0, because the indexed z-origin format carries layer indices with **no spare "no data" value** — `allNanColumn_stillReportsLayerZero_theDocumentedLimit` pins it so changing it is deliberate. **Why that was not fixed too:** an out-of-range index *is* representable and Tool 2 would report `STATUS_UNMAPPED_INDEX` for it, but (a) that status currently means "the mapping is defective", so reusing it for "the producer deliberately says no data" conflates intent with error — contrast Tool 3's `STATUS_NO_DATA`, which exists precisely because the direct-Z format expresses NaN natively; (b) `ZProjector` **cannot compute the layer count** — `project(Mode, List, int[] globalZIndex)` sees only the *present* slices' indices — so emitting one would need a new parameter on a class shared by both input types; and (c) the 16-bit output cannot carry NaN while the 32-bit one can, so the two depths would want to differ, which is exactly the trap p10.9 was written to avoid. Fixing the partial case alone **narrows the silent window from "any NaN in the lowest layer" to "every layer NaN at that pixel"**, which is most of the value for none of the cost.

## Tool 1 — per-timepoint input validation

*Adding or changing a check inside a scanner, for the layers of one timepoint.*

### Accepting a new image type into the projector

- **`ColorProcessor.getf` returns the packed ARGB int, not an intensity — which is why Tool 1 rejects colour input rather than projecting it.** Tool 1 reads raw intensity through `getf` and applies no bit-depth allowlist (the depth is only *recorded*, to normalize the 8-bit raw preview), so before p10.5 a 24-bit RGB dataset sailed through and produced a z-origin map computed from packed colour values — structurally valid output, complete nonsense, no warning. Both input types now reject `getBitDepth() == 24` where they already check dimensions (`ProjectionInputScanner.loadTimepoint` names the Z-layer, `ProjectionStackScanner.projectTimepoint` names the slice), written separately per input type. Grayscale 8/16/32-bit stays unrestricted — that breadth is deliberate, since the projector only ever compares pixels with each other — but since p10.6 all layers of **one timepoint** must share a depth, because that comparison is exactly what breaks: 8-bit tops out at 255 and 16-bit at 65,535, so a mixed timepoint hands Max-Z to the deeper layer on magnitude alone. Depth changes **between** timepoints only log a NOTE (each timepoint is projected independently and the z-origin output stores layer indices, so nothing is corrupted) — a deliberate divergence from Tools 2/3, which reject folder-wide mixing. The stack layout's mixed-depth branch is defensive and untested on purpose: `FileSaver` writes a stack using the first slice's type and coerces the rest, so a mixed-depth stack cannot survive a round-trip to a file (verified against ij 1.54f).

### Handling a timepoint whose size or bit depth differs

- **A timepoint that changes *size* is skipped, not noted — the opposite of a timepoint that changes *depth*, and the difference is downstream survivability.** Both input types check dimensions and bit depth *within* one timepoint (`ProjectionInputScanner.loadTimepoint` per Z-layer, `ProjectionStackScanner.projectTimepoint` per slice), but *across* timepoints only `ZProjectorPlugin.processDataset` can see it, so both cross-timepoint checks live there — the one place both input types already meet, which is why this is not a violation of the write-each-check-per-input-type rule. A **depth** change only logs a NOTE: each timepoint is projected independently and the z-origin output stores layer indices, so nothing is corrupted. A **size** change (added p10.8) skips the timepoint, because it is not survivable: `TiffStackLoader` sizes its pixel array from the first frame and rejects the whole folder if any later frame disagrees (p10.1), so writing one odd-sized timepoint makes the **entire** z-origin folder unloadable by Tool 2, while dropping it leaves only a frame gap — which Tool 2 accepts. The reference size is the **first successfully written** timepoint's (set in the same `written == 0` block that lazily creates the output tree), and the check runs *before* the depth NOTE so a dropped timepoint neither emits one nor becomes the "previous" depth. Skips flow into the existing `total - written` return, so p10.6's run-summary `WARNING` covers them automatically. **The reference is unverified — it is simply whichever timepoint was written first — so if the *outlier* is first, every later timepoint is skipped against it and the run reports a huge skip count while the one survivor is the actual problem.** That inversion is why `dimensionMismatch` names the reference size *and* the timepoint it came from, and why `dimensionSkipSummary` adds a per-dataset `WARNING` that, once the skips are the majority, says outright that the reference is the likelier culprit. Both are pure package-private helpers tested in `ZProjectorPluginTest` — `processDataset` itself stays `private`. **The accounting around the skip is untested and must be re-checked by hand when you touch this loop:** that the skip (1) counts into the `total - written` return, (2) thereby reaches the run-summary `WARNING`, (3) never increments `written` so it cannot read as success, and (4) runs *before* the depth NOTE so a dropped timepoint neither emits a NOTE nor becomes `previousBitDepth`. Those four are precisely what p10.6 got wrong, and no test asserts any of them — see the test-suite note above for why (`processDataset` is `private` and `ZProjectorDialog.Config`'s constructor is package-private in another package, so covering them needs both widened).

### Adding a duplicate-Z check to either scanner

*Records a **costed decision**, not a bug that was hit — filed here because the trigger is the
same code you would be editing, but nothing described below was ever broken.*

- **Duplicate Z is rejected by the stack scanner and accepted by the folder scanner — that asymmetry follows from their internals and is *not* an oversight to "fix".** `ProjectionStackScanner.scanDataset` throws on two slices sharing a Z (`:105-110`) because its `zIndex` is a **`HashMap<Double,Integer>` keyed by Z**: without the check one `put` overwrites the other, both same-Z slices record the surviving index, and the other index is orphaned in the mapping. It needs uniqueness **for its own data structure**. `ProjectionInputScanner` has no such check and **needs none**, because the folder layout keys everything by **position**: `-5/` and `-005/` each get their own global index, both load as separate slices, both compete in the projection, and the JSON maps two indices to the one depth — `ZMappingLoader` accepts that happily (distinct keys). Verified end to end: `zValues = [-300.0, -5.0, -5.0]`, `globalZIndex = [0, 1, 2]`, three slices loaded, winner's index resolving to −5.0. **Nothing is overwritten and the reported Z is correct.** **A folder-side check was costed and declined** (~6 lines beside the sorted `zValues`, no test or fixture affected — every layer name in the suite is distinct): it would prevent **no wrong output**. Both realistic producers — an export with inconsistent zero-padding, or a duplicated backup folder — are cases where the duplicate is *genuine* and today's behaviour is right; and the typo it would catch requires writing the same number two different ways, while the *likely* typo (`-50` for `-5`) yields a distinct Z and is not caught by it at all. Note also that **even the stack path's check protects an internal invariant rather than a wrong answer**: with the check removed, the surviving index still resolves to the correct depth, so the damage there is a redundant mapping entry and two slices sharing an index, not a bad Z. **One documented nondeterminism:** which of two same-Z folder layers wins a tie depends on directory traversal order, so the recorded *index* can differ between machines — both indices map to the same depth, so the *Z* is identical. Cosmetic, stated here so it is not later mistaken for a bug. The README states keeping them apart as a **convention**, explicitly not a rule the tool checks — do not reword that into a promise of enforcement without adding the check.

### Tightening the slice-label number parsing

*Records a **costed decision**, not a bug that was hit — filed here because the trigger is the
same code you would be editing, but nothing described below was ever broken.*

- **`parseZLabel`'s assignment form tolerates trailing text, which yields two silently-wrong depths — both deliberately left alone. Don't re-derive this; the costing is done.** `z = …` stops at the first character that cannot continue the number and ignores the rest, so **`z = 1,5` returns 1.0** (a decimal comma truncates — note type A's `parseZ` *rejects* `1,5` outright, so the same malformed value is refused by one input type and truncated by the other) and **`z:3/401` returns 3.0** (a slice *number* read as a depth). Both are the exact "confidently wrong depth" the method's javadoc says it exists to prevent, and both are silent. **Left as documentation because neither has a known producer.** The comma needs locale-affected acquisition software actually emitting `z = 1,5`; and `z:3/401` is **not** something ImageJ writes into a label — verified as `StackWindow.createSubtitle()` output (`ij/gui/StackWindow.java:255-271`), the *window subtitle* drawn above the canvas, never stored in an `ImageStack` and never written to a TIFF — so it could only arrive from a third-party writer. Three tightenings were costed against every real and test label: **(a)** require the number to end at whitespace/end-of-label (`(?=$|\s)`) — **wrong, do not use**: it breaks currently-accepted forms (`slice 3, z = -400.000, ch 1`, `z = 10.5um`), and its "consistency with the bare form" rationale is false — the bare form rejects trailing text because it must match the *whole* label, whereas the assignment form exists precisely to find a value **inside surrounding metadata**, so trailing-text tolerance is the feature, not an inconsistency. **(b)** forbid a `/` after the number — surgical, nearly free, breaks nothing; take it if a real producer of `z:N/M` labels ever turns up. **(c)** reject only the genuinely ambiguous `[,./]` + digit — catches **both** hazards in one lookahead and keeps every accepted form, at the cost of one false rejection (`z = -400.000, 5 more`). The decision was (b) and (c) both buy protection against unevidenced inputs at a certain cost — a behaviour change, a patch, and a manual Fiji run — so neither was taken; same conclusion as the ignored-sub-folder case, for a different reason (there no honest rule existed; here a clean rule exists but the hazard is hypothetical). **The test cost of tightening later is zero:** the real-data fixture's three labels are the bare assignment form with nothing trailing, and no existing test asserts the tolerance — the only one that looks like it does, `parseZLabel_acceptsLabelledAndBareNumbers_rejectsArbitraryText`'s `"slice 4\nz = -3\nExposure=20ms"`, has a **newline** after the number, which every candidate accepts as a boundary. All of them pass under (a), (b) and (c) alike.

### Testing the stack layout within-timepoint guards

*Records a **costed decision**, not a bug that was hit — filed here because the trigger is the
same code you would be editing, but nothing described below was ever broken.*

- **Two of the stack layout's within-timepoint guards are unreachable while the folder layout's identical ones are tested — that asymmetry follows from how the two layouts are *constructed*, and is not a coverage gap to close.** `ProjectionStackScanner.projectTimepoint`'s per-slice **dimension** and **bit-depth** checks both sit on branches no real input can take, because a stack is one file: ImageJ normalises it on the way in. Depth — `FileSaver` writes a stack using the first slice's type and coerces the rest, so a mixed-depth stack cannot survive a round-trip to a file. Dimensions — note the trap here, since the obvious explanation is wrong: `ImageStack.addSlice` does **not** reject a differently-sized processor, it silently re-frames it to the stack's size (crop or zero-pad, ij 1.54f `ImageStack:106-114`), and `ImageStack.getProcessor` (`:307-334`) then builds *every* processor at the stack's single width/height, so no `ImageStack` can report per-slice sizes at all. Both of `projectTimepoint`'s stack sources are closed independently too: `tryOpenVirtual` requires `info.length == 1`, whose single `FileInfo` is cloned per slice; and the `IJ.openImage` fallback routes a multi-IFD TIFF through `Opener.openTiffStack`, which returns null unless `allSameSizeAndType` (`Opener:800`, comparing width and height at `:783-785`), after which `openTiff2` opens only the **first** IFD (`:1131`) — a 1-slice image, never a mismatched stack. The folder layout's counterparts (`ProjectionInputScanner.loadTimepoint`) *are* tested and must stay so, because there each Z layer is a **separate file opened independently** and nothing enforces a common size or depth — mixing really happens. Keep both stack-side branches: they cost nothing, they are the honest expression of the invariant, and they are what would catch it if a future ImageJ relaxed any of the above. **Do not write tests for them** — verified against ij 1.54f sources plus a live `addSlice` probe; a test could only assert ImageJ's normalisation, not this code.

### Changing where the TIFF-stack input gets its Z

- **Z for the TIFF-stack input comes from slice labels only, and unreadable labels must stay a hard error.** `ProjectionStackScanner.parseZLabel` accepts ImageJ's `z = -400.000` form (anywhere in a possibly multi-line label) or a label that is *nothing but* a number, and returns `null` for anything else — which fails the whole dataset with a message naming the offending slice. It deliberately does **not** fall back to "the first/last number found in the text": a label like `00001-0003.tif` would then yield a confidently wrong depth, silently corrupting every Z coordinate downstream, which is far worse than refusing to run. The calibration (`pixelDepth`/`unit`) is *not* consulted — real Fiji Z-stacks in this pipeline carry `pixelDepth=1.0`/`unit=null` while holding the true depths in the labels, so trusting calibration would look like it worked and be wrong.

## Tool 1 — run accounting & pre-flight

*Editing `ZProjectorPlugin` — the loop over timepoints and datasets, and what it reports.*

### Counting written timepoints in processDataset

- **Tool 1's per-timepoint skip must never add up to a "successful" run — check `written`, not `total`.** `ZProjectorPlugin.processDataset` catches a failing timepoint, logs it, and continues, which is right (one bad file shouldn't kill a long run) — but before p10.6 it then logged `done: N timepoint(s)` using the *attempted* count and let `unitsDone++` run regardless, so a dataset where **every** timepoint failed reported success. It also created the output folders and wrote `z_layer_mapping.json` up front, leaving an empty tree plus an orphan mapping that `TiffStackLoader` would happily accept as an input folder. Three rules now hold and should stay: the output tree and mapping are created **on first success** (lazily), a dataset with **zero** written timepoints **throws** carrying the first failure's message, and any skipped timepoint raises a `WARNING` in the run summary — because a dropped timepoint is indistinguishable downstream from a legal frame gap, which Tool 2 accepts silently.

### Wording the end of a projection run

- **A run that produced nothing must not end on "complete" — `unitsDone == 0` is a failure, and the only case whose run-level wording changes.** p10.6 fixed the *counts*; p10.9 fixed the *framing* around them, once the pre-flight name checks made "refused before writing anything" a common outcome. A single-scope run whose only dataset is refused used to end on `IJ.showStatus("Z-Projection complete.")` plus `Done. 0 / 1 unit(s) processed`, with the sole failure signal a `WARNING` between them — accurate but inverted in emphasis, and invisible to anyone who doesn't open the Log. When `unitsDone == 0`, `run()` now sets a failed status, logs `FAILED — nothing was written.`, and pops `IJ.error`, following the `noDatasetsMessage` precedent in that same method. Three rules to keep: the dialog is **self-contained** (`writeNothingMessage` carries the reasons, because `IJ.error` is **modal** — one that says "see the Log" while blocking the Log is worse than none, which is also why `failures` is accumulated in the loop); it is **word-wrapped** by `wrapForDialog`, because `MessageDialog` renders through `MultiLineLabel`, a lone `StringTokenizer(text, "\n")` with no wrapping, so a 200-char line becomes a dialog wider than the screen (blank lines must stay a single space — `StringTokenizer` skips truly empty tokens); and it is **capped** at `MAX_FAILURES_IN_DIALOG` with the omitted count stated, never silently truncated. `IJ.showProgress(1.0)` is deliberately kept — `ProgressBar.show` treats `progress >= 1` as *finished* and **clears** the bar, so it does not leave a misleading full one (verified in ij 1.54f sources). **Do not generalise this to runs that wrote something:** `SKIPPED` is the right per-dataset verb when other datasets succeeded, and a partial run's existing wording is untouched on purpose.

### Adding a cross-timepoint check to the projector

*Records a **costed decision**, not a bug that was hit — filed here because the trigger is the
same code you would be editing, but nothing described below was ever broken.*

- **Tool 1's cross-timepoint checks are input-type-independent *by construction*, so hand-testing one input type validates both — but that rests on one upstream detail.** All four p10.8/p10.9 additions — `missingTimepointIndexError`, `duplicateTimepointIndexError`, `dimensionMismatch`/`dimensionSkipSummary`, and `run()`'s `unitsDone == 0` write-nothing framing — live in `ZProjectorPlugin` *above* the `ProjectionSource` abstraction and consume only `timepointLabels()` or `projected.result`. `ZProjectorPlugin` names a concrete scanner in exactly three executable places — `resolveDatasets` (batch dataset detection), `openSource` (construction), and `run()`'s unconditional `ProjectionInputScanner.resetIgnoredSubFolderReport()` — and everything downstream is typed `ProjectionSource`, so no per-type branch exists that could bypass them. The third is not a check and carries no data: it marks the run boundary for the ignored-sub-folder note (see [Handling a sub-folder that is not a Z layer](#handling-a-sub-folder-that-is-not-a-z-layer)), and the stack input type simply never populates that state, so it introduces no per-type behaviour either. The same reasoning applies to the `processDataset` accounting gap documented above: it is type-independent too, so hand-testing the *other* input type would not close it. **The dependency to watch:** `duplicateTimepointIndexError`'s correctness for the **folder** layout rests on `ProjectionInputScanner.scanDataset` accumulating the timepoint-filename union into a **`TreeSet`** (original p8.0 code, noted at the point it is built). One timepoint present in twenty Z-layer folders must arrive as **one** label; swap that for a plain `List` and every well-formed folder dataset is refused as an index collision. No test asserts any of this: type-independence is a property of *where the code sits*, not a behaviour that can be exercised, and the only test that would prove it end-to-end needs the `processDataset`/`Config` visibility widening already ruled out.

### Handling a timepoint filename with no digits

- **A timepoint filename with no digits is malformed input, refused before any output is written — and the reason is the missing timepoint index, *not* what Tool 2 does with it.** A timepoint's identity **is** the number in its filename: that is what states its position in the sequence, so a digit-free name like `cells.tif` means the file carries no timepoint index and the dataset has no timepoint ordering at all. `missingTimepointIndexError` (p10.9) checks every name in `ProjectionSource.timepointLabels()` **before any projection or output work** and throws listing *all* offenders at once, mirroring `TiffStackLoader.load`'s up-front full-offender-list style (p10.2). **Frame the message this way round and keep it that way.** Leading with Tool 2's last-digit-run rule reads like a consumer quirk someone might try to work around; the downstream damage is a *symptom* of the missing index, so it stays as supporting detail below the lead. That framing also makes the check **depth-independent by construction** — `missingTimepointIndexError` takes no bit-depth arguments at all, so there is no policy to keep in sync; don't add any. The supporting detail is worth knowing because the two depths break differently: the 16-bit `z_origin_cells.tif` carries no digit run and `TiffStackLoader.load` refuses the folder (p10.2), while the 32-bit `z_origin_32bit_cells.tif` **does** carry one — the `32` of `32bit` — which "last digit run anywhere" reads as frame **32**, so mixed with normally-named timepoints (`cells.tif` + `0007.tif` → frames 32 and 7) the folder **loads with no error at all** and that timepoint silently sits at frame 32, its Z attached to the wrong frame. All three consumer-side outcomes are pinned by seam tests in **`ProjectionExporterTest`** (`seam_digitless32BitName_loadsSilentlyAtFrame32_...`, `..._isOnlyRefusedWhenItCollidesWithAGenuineFrame32`, `seam_digitless16BitName_isRefusedOutright`), in the **producer's** suite beside the existing project→extract seam test and going through the real `ProjectionExporter.write*Origin` calls so the output *names* are the exporter's own rather than hand-typed. **Why a hard error and not a skip** (p10.8 shipped it as a per-timepoint warn-and-write, replaced in p10.9): a skip manufactures a frame gap, which Tool 2 accepts silently; and since input naming is normally uniform, the realistic case is *every* timepoint offending, so skipping them all writes nothing — which p10.6 already established must throw. Nothing loadable is lost by refusing (16-bit was never loadable, 32-bit was only ever wrong), though note the always-written 8-bit `raw/` preview is withheld too. The check only asks "is there a digit?", exactly as `TiffStackLoader.hasFrameNumber` does; do not make it smarter about *where* the digits sit, or it will disagree with the consumer whose behaviour it explains.

### Ordering the pre-flight name checks

- **The two pre-flight name checks must stay in order: digit-free first, duplicate-index second — the second is depth-independent only *because* the first ran.** `duplicateTimepointIndexError` (p10.9) refuses a dataset where two labels resolve to the same timepoint index (`run1_0007.tif` / `run2_0007.tif` → both 7), the producer-side twin of p10.4's loader check, with the same "two files cannot hold one position in the sequence" framing as the digit-free case. It is **not** a correctness fix — p10.4 already refuses such a folder loudly at load — it just fails in seconds instead of after a full projection run. The ordering is load-bearing: it computes the index from the **label**, which is sound only because every label reaching it carries a digit run of its own, so that run always sits *after* the `z_origin_32bit_` prefix and wins the last-digit-run rule identically for `z_origin_<label>` and `z_origin_32bit_<label>`. For a **digit-free** label there is no such run, and the only digits in the output name would be the `32` of `32bit` — which differs between the depths. Refuse digit-free names first and the duplicate check needs no depth argument at all; reorder them and it silently becomes depth-dependent. Verified against `TiffStackLoader.extractFrameNumber`: `z_origin_run1_0007.tif` and `z_origin_32bit_run1_0007.tif` both give 7, and `z_origin_0007_run1.tif` gives **1** — the *last* run, so this check must take the last run too, not the first. Grouping is by **numeric value**, not raw digit text, since `z_7.tif`/`z_0007.tif` collide while `z_0008.tif` does not (p10.4 draws the same distinction); leading zeros are stripped rather than parsed, giving `Integer.parseInt`'s equivalence classes without an overflow crash on an absurd digit run.

### Handling a sub-folder that is not a Z layer

- **A sub-folder the folder input type does not read as a Z layer is a NOTE, never an error — and its once-per-run dedup state must not cross the `ProjectionSource` boundary.** `ProjectionInputScanner.scanDataset` accepts only sub-folders whose whole name parses as a number, so `notes/`, `QC/`, `_backup/` are correctly ignored — and so is a genuinely misnamed `z-298/`, which before this was dropped in total silence. **Warning, not error, and the reason is that no rule can tell the two apart**: every heuristic (does it hold TIFFs? does it look number-ish?) fails in a realistic direction, and refusing a sensibly-organised dataset over a `QC/` folder is a worse outcome than the problem. So the note states what was ignored and what a misnamed layer would cost, and leaves the judgement to the user. **Get the consequence right — a dropped layer does *not* shift the Z indices.** `DatasetScan.zValues` and `zLayerNames` are built from the same filtered layer list, so an index and the depth it maps to stay mutually consistent; what is lost is that the dropped layer never competes in the projection, so a pixel whose true extremum lay in it is attributed to the nearest surviving layer instead — wrong in both the z-origin map and the raw projection — while every pixel whose extremum was in a surviving layer is exactly right. Partially-correct output is why it is worth saying at all. **Placement is the constrained part:** the rejected names exist nowhere but inside `scanDataset`, and threading a collector up through `ProjectionSource` would put type-specific state on the very boundary that makes the cross-timepoint checks type-independent (see [Adding a cross-timepoint check to the projector](#adding-a-cross-timepoint-check-to-the-projector)). So the dedup set is **static, private, inside the scanner**, and the note goes sideways to `IJ.log` exactly as that class's failures go sideways to `IOException` — nothing flows upward. The price is that the run boundary has to be signalled from outside: `resetIgnoredSubFolderReport()`, called once at the top of `run()`. **Do not drop that call** — without it the dedup silently becomes once per *Fiji session*, so a second run says nothing about the folders the first one described. `isDataset` deliberately does **not** report: batch mode calls it on every sub-folder of the input root, most of which are not datasets at all. `reportIgnoredSubFolders` returns its lines rather than logging them so the wording and the dedup are testable without capturing `IJ.log`; `scanDataset_feedsItsRejectedSubFolderNamesToTheReport` proves the wiring by observing the dedup state instead. **The note cannot reach a batch candidate folder with *zero* numeric layers.** `resolveDatasets` gates on `isDataset`, which is false for a folder holding only `z-300/`/`z-299/`, so it is skipped before `scanDataset` ever runs and no note is emitted. Single scope does not consult `isDataset`, so the same folder there throws and names the rejected sub-folders. The uncovered case is therefore precisely: a batch run in which other datasets succeed and one candidate folder is entirely misnamed — skipped in silence. Closing it would mean reporting from `isDataset`, which batch calls on every sub-folder of the input root, most of which are not datasets at all.

## Tools 2/3 — loading stacks & mappings

*Editing `TiffStackLoader`, `TopoJStackLoader` or `ZMappingLoader`.*

### Reading a 32-bit indexed TIFF pixel

- **A `NaN` in a 32-bit indexed TIFF must never reach `Math.round` — it becomes 0, which is the lowest-Z layer's own index. This is p10.11's bug one tool downstream.** `TiffStackLoader.readFrameInto` reads 32-bit frames as `Math.round(ip.getf(x,y))`, and `Math.round(Float.NaN)` is **0** in Java. Index 0 is a **legitimate mapping key**, so before p10.12 a NaN pixel resolved to a real depth, was reported `STATUS_OK`, counted valid, and written to `.npy` — the worst failure class in this pipeline, and *exactly* the mechanism, invisibility and consequence of the p10.11 `ZProjector` bug. Fixed by mapping NaN to `TiffStackLoader.NO_DATA` before rounding. **The fix is two lines because nothing downstream needed changing**, and that rests on a construction-level guarantee worth not re-deriving: `ZMappingLoader`'s entry pattern captures keys as `"(\d+)"` — **digits only, no sign** — so a mapping key can *never* be negative, making any negative sentinel unmappable by construction rather than by luck. `ZExtractor.indicesToZ` then turns it into `NaN` → `STATUS_UNMAPPED_INDEX`, counted in `numUnmapped`, logged, dropped from 3-D only (2-D is unaffected, since `valid2D.add(i)` precedes the Z check). **`ZExtractor` contains no reference to `NO_DATA`** — deliberately; the constant is `public` only so a future patch could tell a NaN pixel from an infinite one without a signature change. **Why `-1` and not `Integer.MIN_VALUE`:** `Math.round` already maps −Infinity to `Integer.MIN_VALUE` and +Infinity to `Integer.MAX_VALUE`, and **both already fail loudly today** (neither is a mappable key) — so NaN was the *only* broken value, and `-1` keeps it distinguishable from an infinite pixel. **16-bit cannot hit this at all**: a `ShortProcessor` read via `getPixel` is an unsigned `0–65535` int with no NaN representation, so this is strictly a 32-bit concern and the check sits inside the 32-bit branch. **Tool 3 is unaffected by design, not by luck** — `TopoJStackLoader` stores `float[][][]` and reads `getf` *without* rounding, so NaN survives natively and `STATUS_NO_DATA` exists precisely to express it; that is the indexed-vs-direct-Z architectural difference, so there is nothing to duplicate and the write-each-guard-per-loader rule is not engaged. **There is NO known producer, and it was taken anyway.** Tool 1 writes integer layer indices; the Python reference scripts write integer indices (`np.argmax`); a mis-selected TopoJ folder fails loudly on nearly every pixel (µm values round to unmapped indices) with only its no-data pixels slipping through. An external float z-origin map using NaN for "no data" — precisely what p10.11 documented Tool 1 as *unable* to express — is coherent but unevidenced. Taken regardless because the cost is two lines and the failure class is the worst in the pipeline; **do not read this as precedent that unevidenced hazards get guards** — it is the cheapness that carried it, see [Tightening the slice-label number parsing](#tightening-the-slice-label-number-parsing) and [Adding a duplicate-Z check to either scanner](#adding-a-duplicate-z-check-to-either-scanner) for the same test reaching the opposite answer.

- **Correction (p11.8) — the "fails loudly" clause above is false, and the case it dismisses is silent.** *Appended rather than edited, per this file's rule; the original stands above as what was believed at p10.12.* Established against the code during p11.6, not inferred: `TiffStackLoader` accepts **32-bit float** (`:153`), which is exactly what a TopoJ height map is; the 32-bit branch reads `getf` and applies `Math.round` with **no complaint for a non-integer value** (`:250-251`); and p10.31's full-dataset histogram found **every TopoJ value to be an integer in `1..nSlices-1`** — the shape of a valid layer index. So against a `z_layer_mapping.json` of comparable depth **every pixel maps**, the run reports `STATUS_OK` throughout, and it writes a complete `.npy` that is wrong everywhere, with nothing logged. **The clause was doubly wrong, and the second half is the instructive one:** its stated reason — *"µm values round to unmapped indices"* — assumed a TopoJ pixel holds µm, which **p11.0 established it never did**; and even granting that belief, only the *negative* µm values would have failed to map, not "nearly every pixel". A claim can be false both in what it asserts and in the reason it gives, and the reason is the half that survives into other arguments. **No guard is being added, and that is a position rather than an oversight.** Pairing the right folder with the right tool is the **user's** responsibility: the loaders check bit depth, not provenance, and nothing in a TIFF says which tool wrote it. The plugin's job is to process correctly the data it is given, not to authenticate its origin — any check that tried would have to infer provenance from pixel values, which is the confidently-wrong-answer failure class this project refuses everywhere else. **What this does and does not disturb above:** the clause was one of four in the *"NO known producer"* enumeration, and **that conclusion survives** — p10.31 measured **zero NaN** across 636,893,388 pixels of the reference dataset, so a TopoJ folder is not an evidenced producer of the NaN pixels *this* guard exists for, which is the question the enumeration was actually asking. The guard's own justification is untouched: it rested on cheapness and failure class, not on this clause. What the correction does expose is a **different** hazard, outside this entry's subject — a wrong-tool pairing corrupts Z through the pixels that map *correctly*, which no NaN sentinel can see. **`docs/CHANGELOG.md`'s p10.12 row carries the same sentence and is deliberately left uncorrected**, because rows are never edited; if you find it there, it was seen and not missed.

### Reading 16-bit versus 32-bit indexed pixels

- **16-bit and 32-bit indexed TIFFs.** `TiffStackLoader` stores pixels as `int[][][]`. 16-bit frames read via `ImageProcessor.getPixel(x, y)`, which already returns the correct unsigned `0–65535` value. 32-bit frames are backed by a `FloatProcessor`, so indices are read via `getf(x, y)` and rounded with `Math.round()` — using `getPixel` on a float processor truncates toward zero and can be off-by-one. Mixed bit depths within one folder are rejected with a clear error; only 16-bit and 32-bit are supported (8-bit and 24-bit RGB are rejected). Since p10.1 a frame whose **pixel dimensions** differ from the first frame's is rejected too — see [Relaxing the per-frame dimension check](#relaxing-the-per-frame-dimension-check) for why that one had to be a hard error.

### Relaxing the per-frame dimension check

- **Every frame's dimensions are checked against the first frame's, in both extractor loaders — do not relax this into a crop/pad.** `TiffStackLoader` and `TopoJStackLoader` both size their pre-allocated pixel array from `tifFiles[0]` and, until p10.1, validated only *bit depth* per frame. That made a mismatched frame fail in two different ways depending on the accessor, which is the part worth remembering: **`ShortProcessor.getPixel` is bounds-checked and returns `0`** outside the image, while **`FloatProcessor.getf` is not bounds-checked at all** — it indexes `pixels[y*width + x]` with the *processor's* width and no guard. So a short 16-bit frame silently zero-filled, and because index 0 is a valid mapping key for the **lowest-Z layer**, affected detections got a real-looking Z with `STATUS_OK`, counted valid and written to `.npy` with nothing logged — the worst failure class in this pipeline. The 32-bit paths (both tools) instead sheared rows and usually died with a bare `ArrayIndexOutOfBoundsException` (on Fiji's Java 8 its `getMessage()` is just the index, so the dialog showed a naked integer). A *larger* frame reads in-bounds and would silently become a top-left crop. All of it is now one `IOException` naming the file and both dimension pairs — which makes the larger-frame case **technically breaking**: a dataset that used to load (cropped) now stops at load time. **This guard was the single deliberate exception to Tool 2's isolate-per-tool freeze *as of p10.1*** — it is written separately in each loader, with no shared helper, precisely so the exception stays narrow. Note the scope of that claim: it is **superseded** as a statement about the present. p10.2 (missing frame number), p10.4 (duplicate frame number) and p10.12 (the NaN sentinel) have all since modified `TiffStackLoader`. What survives is the *rule the exception established* — a guard needed by more than one loader is written separately in each, never behind a shared helper — not the "single exception" count.

### Extracting the frame number from a filename

- **Frame-number extraction uses the LAST digit run in the filename, not the first — and a frame number must be both present and unique, never defaulted and never silently overwritten.** `TiffStackLoader.extractFrameNumber` (Tool 2) must not just take the first regex match — filenames can contain incidental numbers before the real frame index (e.g. `z_origin_32bit_0007.tif`, where "32" from "32bit" is not the frame number). Taking the first match collapses every file to the same detected frame. **Tool 3 (`TopoJStackLoader`) looks in a different place on purpose** — for filename flexibility it anchors the frame index to the integer the base name (extension stripped) **ends with** (`(\d+)$`): any prefix, any zero-padding width (not hard-coded — `frame7.tif`, `topoj_0007.tif`, `height_map_00000100.tif` all work). **Keep that where-to-look difference**; it is deliberate and neither loader should drift toward the other. Where they *do* agree is on rejecting the two ways a `frame → stackIndex` map loses files, both checked up front in `load` before sorting, both throwing with **every** offending filename named: (1) the **missing** case (Tool 2 since p10.2, Tool 3 since p9.4) — a name carrying no frame number at all. `extractFrameNumber` still returns 0 for a digit-less name in Tool 2, but frame 0 is itself a legitimate frame number, so that value cannot double as an error signal. (2) the **duplicate** case (both since p10.4) — two names resolving to the *same* number, which `frameToIdx.put` would silently overwrite, leaving the earlier file unloaded and the stack quietly shorter than the folder. Note the duplicate check must group by the resolved number, not compare filenames: mixed zero-padding widths (`z_7.tif`, `z_0008.tif`) are legal and distinct. All of these guards are written **separately in each loader, with no shared helper**, same as p10.1's dimension guard.

### Parsing the Z-mapping JSON

- **A duplicate key in the Z-mapping JSON is refused, not silently last-wins — the last place a duplicate was still accepted quietly.** `ZMappingLoader` built its map with `mapping.put(index, zValue)`, so `{"0": -600.0, "1": -599.0, "0": -1.5}` parsed with index 0 at **−1.5** and nothing said so. p10.4 (two TIFFs resolving to one frame number) and p10.9 (two timepoints claiming one index) both refuse the analogous collision loudly, naming every offender; p10.13 makes the mapping consistent with them, listing each repeated index with **both** values. Repeats are refused even when the two values are *equal* — a file that states one layer twice is malformed regardless, same as p10.4 treats two files resolving to one frame. **The interaction worth knowing:** the parser is a regex over the **whole file**, not a JSON parser, so a stray `"<index>": <value>` anywhere — including in a comment or outside the main object — counts as an entry and can now *collide* with a real one, turning a previously-working file into a refused one. That tolerance is unchanged and still useful, but it is no longer free, so the error message states it outright rather than leaving the user to wonder why a note broke their mapping. Note the older test named `load_ignoresNonEntryContentAroundValidEntries` only exercises whitespace and braces — it does **not** pin the strong "arbitrary surrounding text" form, which is why adding this check broke nothing. **Known remaining item, not fixed:** the key is read with `Integer.parseInt` on the `\d+` capture, so an absurdly long digit run throws an uncaught `NumberFormatException` rather than a clear message — its own patch.

## Tools 2/3 — sampling & extraction

*Editing `ZSampler`, `TopoJSampler`, `ZExtractor` or `TopoJExtractor`.*

### Reporting why a detection produced no Z

- **Out-of-bounds position vs. missing frame are different root causes — don't conflate them.** `ZSampler` silently drops any sampled pixel outside `[0,width) x [0,height)` rather than clamping or erroring; near an image edge, RADIUS's disk and FOUR_NEIGHBOR's corners can get **clipped** (fewer samples than usual), and a detection whose (x,y) is far off-grid returns **zero** samples from every method, exactly like a genuinely missing TIFF frame does. `ZExtractor.extract` disambiguates the zero-sample case by checking `stack.frameToIdx.containsKey(csvFrame+frameOffset)`: if the frame exists but sampling still failed, it's counted in `ExtractionResult.outOfBoundsCount`; if the frame itself isn't in the stack, it's `missingFrameCount`. Both `ZExtractor`'s per-run log line and `ZTrackerPlugin.logExtractionSummary` report them separately — a bad detection X/Y (fix: check the CSV) and a frame-offset problem (fix: revisit Step 4) look identical as a symptom (NaN Z) but need different fixes, so don't re-merge these into one counter. Per-detection, the *reason* for a NaN Z (`ExtractionResult.STATUS_MISSING_FRAME` / `STATUS_OUT_OF_BOUNDS` / `STATUS_UNMAPPED_INDEX`, or `STATUS_OK`) is stored in the parallel `ExtractionResult.sampleStatus` array, so downstream code (export, logging) can explain *why* a specific point failed, not just that it did.

- **The status list just above names four of six, and was already incomplete when written (appended p11.8).** `ExtractionResult` defines **six** `STATUS_*` constants. Missing from that sentence are **`STATUS_NO_DATA`** — Tool 3's direct-Z analogue of `STATUS_UNMAPPED_INDEX`, set when pixels were sampled but every one was NaN, which since p11.0 most often means `TopoJStackDecoder` refused an ambiguous `1.0` sentinel rather than that the map held no depth there — and **`STATUS_INVALID_XY`**, set when the detection's own X or Y is NaN so sampling is never attempted at all (see [Sampling by rounded coordinates](#sampling-by-rounded-coordinates)). Both belong here for the reason this entry exists: they are **distinct causes with different fixes**, and a list that omits them invites exactly the conflation the entry warns against — a reader working from those four would have nowhere to file a `noData` drop. **This is the failure form no phrase-level search can find:** nothing in the sentence is false, the *omission* is, so the only check is to count the list against `ExtractionResult`'s constants. Counted at p11.8: four of six.

### Reading the radius column or sizing the sampling disk

- **`Double.parseDouble` accepts `"NaN"` and `"Infinity"` — the radius column needed the same guard X/Y already had, and the infinite case is a *hang*, not a wrong number.** `TrackCsvLoader.parseCoordinate` explicitly rejects a literal `NaN` for X/Y (its javadoc says why); `parseDoubleOrDefault`, three lines away, did not, so a radius cell reading `NaN` or `Infinity` sailed past the `catch` and became a real `NaN`/`Infinity` radius (p10.13). The two break differently and the second is the serious one: a **NaN** radius makes `ZSampler.sampleRadius` take zero samples, and the detection is then reported `STATUS_OUT_OF_BOUNDS` — sending the user to check coordinates or the Step-4 offset when the fault is a radius cell. An **infinite** radius gives `(int) Math.ceil(Infinity) == Integer.MAX_VALUE`, so the disk loop runs `dy,dx = -2147483647 … 2147483647` — about **1.8 × 10¹⁹ iterations, freezing Fiji with no error and no progress** (found by a probe that had to be killed). Both now fall back to the default. **The parse guard cannot reach the finite case at all:** `1e300` is a *positive finite number*, so it passes `parseRadius` unchanged and still ceils to `Integer.MAX_VALUE`. Hence p10.13 also **clamps the disk radius at the frame diagonal**, `ceil(sqrt(w² + h²))`, in `ZSampler.sampleRadius` **and** `TopoJSampler.sampleRadius` — written separately in each with **no shared helper**, per the p10.1 precedent for a guard both samplers need. The diagonal is the *provably sufficient* ceiling: from any anchor the farthest in-bounds pixel is at most one diagonal away, so beyond it no additional pixel can ever be reached. **The clamp is therefore lossless, not a correction of bad data** — it changes no result for any radius the image can actually hold; it only declines to spend 1.8 × 10¹⁹ iterations rediscovering that the answer is "the whole frame". **Do not turn it into a refusal:** `sampleRadius` returns `double[]` and has no error channel but an exception, which would abort the whole run over one CSV cell — contradicting the rule that a bad detection drops that point and never the run. Reporting an oversized radius *per detection* (in `ZExtractor`, where per-detection status already lives) is a separate open question, deliberately not taken. Both clamp tests would **hang rather than fail** if the clamp were removed, which is the only way to test a non-termination guard. **Non-positive radii are folded in too, and the rule is now simply "a positive finite number, or nothing":** leaving them out left an arbitrary split, since `-1.0` and below make the loop never run (zero samples → the same misattributed out-of-bounds) while `-0.4` and `0` ceil to 0 and quietly sample exactly one pixel, succeeding as though `SINGLE_PIXEL` had been chosen. The silently-*succeeding* case is the worse of the two, which is why `<= 0` is treated as absent rather than only `< 0`. Note this makes `0` a substitution where it previously sampled one pixel. **And the substitution is never silent** — `parseRadius` returns `null` and the *caller* counts it, so the load logs how many rows used the default and names the first `MAX_BAD_RADIUS_LISTED` offending cells by line number and raw text (`line 2: "-1.0"`), with the remainder counted. Substituting a value the CSV did not state is itself a quiet failure if unreported; note these rows are **kept**, unlike the `skippedNaN`/`skippedBadXY`/`skippedOther` counters beside it, so the wording says so. Note also that `TrackData.radius` is **never NaN** from the loader — a missing column or a bad cell substitutes `defaultRadius` — so do not test radius values to detect a missing column; use `hasRadiusColumn()`. The old javadoc claimed the opposite and misled a p10.12 probe fixture.

### Changing the pixel coordinate convention

- **The pixel coordinate convention default flip (p7.0) can change in/out-of-bounds status near frame edges.** `ZSampler.PixelConvention.PIXEL_CORNER` (floor to the containing cell) is now the Step-5 default, replacing the plugin's original `PIXEL_CENTER` (round to nearest) behavior — Center remains fully available as the alternate. Near zero or negative coordinates the two conventions can disagree about whether a detection is even in-bounds: `x=-0.4` rounds to `0` under Center (in-bounds) but floors to `-1` under Corner (out-of-bounds) — `Math.round` and `Math.floor` diverge for any negative non-integer value. **This is not a bug to "fix" by matching one convention's bounds behavior to the other** — it's an inherent, expected consequence of the two conventions disagreeing about which pixel a point belongs to, so don't special-case it away. If a user reports detections newly failing with `STATUS_OUT_OF_BOUNDS` after upgrading, the fix is switching the Step-5 convention back to Center (if that matches their tracker's own coordinate convention), not patching `ZSampler`'s bounds check.

### Sampling by rounded coordinates

- **`Math.round(Double.NaN) == 0` in Java — a silent trap for any code sampling by rounded coordinates.** `ZExtractor.extract` used to call `ZSampler.sample(stack, track.x[i], track.y[i], ...)` unconditionally, with no check for `NaN` X/Y first. Since `ZSampler.sampleSinglePixel`/`sampleRadius` round `x`/`y` via `Math.round`, a `NaN` X was silently treated as `x=0` and produced a **real, "successful" `STATUS_OK` Z value** at a phantom pixel — not a failure. `TrackExportManager`'s own `Double.isNaN(track.x[i])` check (checked on the *original* coordinate, not the sampled result) still caught and dropped these before they reached any exported file, so `.npy` output was never wrong — but `ZExtractor`'s own log line and `ExtractionResult.countValid()` overcounted "valid" detections, and any future caller of `ExtractionResult` that doesn't route through `TrackExportManager`'s filter would get bogus data. Fixed by checking `Double.isNaN(track.x[i]) || Double.isNaN(track.y[i])` at the very top of the per-detection loop, *before* calling `ZSampler.sample` at all — marks `ExtractionResult.STATUS_INVALID_XY`, increments a new `invalidXYCount`, and both `ZExtractor`'s per-run log line and `ZTrackerPlugin.logExtractionSummary` report it. Regression-tested by `extract_nanX_isNeverSampled_notTreatedAsPixelZero`, which plants a distinctive marker value at pixel `(0, y)` and asserts it's never read.

## CSV input

*Editing `TrackCsvLoader` or the column auto-detection.*

### Supporting a new tracking CSV format

- **CSV variety.** TrackMate CSVs have a header row followed by **3 metadata rows that must be skipped**. But not all inputs are TrackMate — some come from other trackers (e.g. columns `Track n°`, `Slice n°`, 1-based frames, latin-1 encoding, no metadata rows). Keep column detection **alias-based and tolerant**, not hard-coded to TrackMate.

### Handling a row with unparseable X or Y

- **Unparseable X/Y at CSV load time is counted and logged, not silently swallowed.** `TrackCsvLoader.load` used to catch `NumberFormatException` around X/Y/Frame parsing together with a bare `// Silently skip malformed rows` — a row with a blank, garbage, or literal `"NaN"` X/Y (Java's `Double.parseDouble("NaN")` **succeeds**, returning `Double.NaN`, so it doesn't even throw) vanished with zero visibility. X/Y parsing is now isolated via `parseCoordinate` (returns `null` for blank/unparseable/NaN) with its own `skippedBadXY` counter and log line (`"Skipped N rows with missing/unparseable X or Y."`), mirroring the existing `skippedNaN` (Frame/Track_ID) counter. Genuinely malformed Frame/radius data still falls through to a separate `skippedOther` counter.

## Export

*Editing `TrackExportManager` or any of the exporters.*

### Deciding what a bad detection removes from an export

- **A single bad point does NOT discard its whole track — only that point is dropped, from whichever export(s) it actually breaks.** `TrackExportManager.export` used to skip the *entire* track's 3D export if any one detection had a NaN Z (and, separately, used to skip the whole track from *both* 2D and 3D if any detection had a NaN X/Y); both whole-track exclusions are gone. There is also no whole-track quality filtering at all (no minimum-length or max-Z-std cutoff) — `TrackExportManager` exports every track it's given. Per point: an invalid X/Y (missing/unparseable position) drops that point from **both** 2D and 3D — a point with no position can't be placed in either — while a NaN Z (missing TIFF frame, out-of-bounds position, or every sampled index unmapped) drops it from **3D only** (2D never depended on Z). 2D and 3D are gated independently: each is skipped for a track only if it has **zero** valid points remaining for that dimension, tracked separately as `2D(noValidPoints)` / `3D(noValidPoints)`. **Note the 3D label is not "noValidZ"** — a 3D point requires both valid X/Y *and* valid Z, so a 3D shortfall can come from X/Y drops alone (with every Z perfectly fine), Z drops alone, or a mix; calling it "noValidZ" would misattribute the cause when X/Y is actually why. Covered by `export_summaryLine_reportsNoValidPointsSkipsSeparatelyFor2DAnd3D` and `export_invalidXYAndInvalidZInSameTrack_dropReasonsDoNotConflate` (the latter also confirms the two drop-reason tallies never conflate when both occur in the same track). The invalid-X/Y drop reason lives in `ExtractionResult.STATUS_INVALID_XY` — both `ZExtractor` (see [Sampling by rounded coordinates](#sampling-by-rounded-coordinates)) and `TrackExportManager` (as a defense-in-depth re-check on `track.x[i]`/`track.y[i]` directly, for `TrackData` built without going through `ZExtractor`) reference the same shared constant, rather than each having their own string. A per-track report is logged on **every** export run (not just when something's wrong) via `TrackExportManager`'s own `[TrackExportManager] ── Per-track report ──` block — one line per track covering 2D and 3D separately, capped at 50 (`MAX_TRACKS_LOGGED`, same convention as `FrameAligner`'s per-track table), ordered by track id (numeric-aware, same `compareTrackIds` convention). The same report, **uncapped**, is also written to `export_report.txt` in each export's `outDir` (so per method-combo subfolder when multiple methods run), since the Fiji Log view's cap is for on-screen readability, not data loss. **Dropping a point never renumbers the surviving frame numbers** — both 2D's and 3D's `T` column always hold each kept detection's real `track.frame[i]`, so a dropped point leaves a genuine gap in the frame sequence (e.g. `0,1,3` if frame 2 was dropped) rather than a shift/compaction (never `0,1,2`) — this is intentional and covered by dedicated tests (`export_droppedPointFromMidTrack_leavesGenuineGapInFrameNumbers_notRenumbered`, and the X/Y equivalent `export_trackWithOneBadXYPoint_dropsFromBothDimensionsButKeepsTrack`) so it doesn't regress.

### Reading the per-track export report

- **The per-track report/`export_report.txt` is generated on every export run regardless of Step-6 format checkboxes, but its 2D/3D wording is npy-specific.** The per-detection classification (`valid2D`/`valid3D`, drop-reason tallies) and the report/file-writing calls all run unconditionally — none of them are gated on `config.exportNpy`/`exportResultsTable`/`exportRoiSet`. But `buildDimensionPart` prints `"2D ✗ (npy export off)"` / `"3D ✗ (npy export off)"` whenever `config.exportNpy` is false, for **every** track regardless of whether that track's points were actually fine — because the 2D/3D verdict is specifically about the `.npy` output, which never ran. Similarly, The summary line's drop-reason counters are plain locals inside `export` (no `ExtractionResult` field is involved), and since p10.13 they include `noData=` — Tool 3's `STATUS_NO_DATA` reached the per-track report, which merges the raw status string, but had no branch in the summary's `else if` chain, so such a drop was counted in **no** summary bucket at all. Adding it needed no `ExtractionResult` constructor change, hence nothing about Tool 3's construction or its tests moved. `exported2D`/`exported3D`/`skipped2DNoValidPoints`/`skipped3DNoValidPoints` in the summary line only ever increment inside the `exportNpy` block, so they stay `0` even when Results Table CSV / ROI zip succeed for every track — those two counters are npy-only, not "any export succeeded." Since Results Table CSV and ROI zip aren't split into 2D/3D (a single flat table with an optional Z column, using the same `valid2D` point set 2D npy uses), `buildTrackReportLine` appends a **separate trailing segment** — `"| Results Table+ROI: N/M pt"` — whenever either is enabled, so a track's line doesn't read as "nothing was exported" when npy is off but another format is still capturing its points. This segment is independent of the 2D/3D verdict and appears (or not) based purely on `config.exportResultsTable`/`exportRoiSet`.
