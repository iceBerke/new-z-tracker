# Deferred decisions — costed and consciously left

Each entry below was **costed and consciously left**; none is an oversight. Re-deriving the
reasoning is the waste these entries exist to prevent, so each records what it would take, what it
would cost, and what would change the answer.

These are the genuinely **open** items — known, understood, still undone. They are not the same as
the costed decisions that are already *closed*: those live beside the code they concern, in
`docs/GOTCHAS.md`, each marked in italics as recording a decision rather than a bug.

**Nor are they the same as `docs/BACKLOG.md`**, which holds work that is *wanted but not yet
done* — "yes, eventually". Everything here has been **costed and declined**: "no, and here is
why". Each entry names what would change the answer; if that actually happens, the item moves to
the backlog.

`CLAUDE.md` carries a one-line index routing here. As with the gotchas, entries are appended and
extended rather than rewritten — an entry quietly kept current stops being a record of what was
decided and when.

---

- **Per-detection reporting of an oversized radius ("option (b)") — the other half of p10.13's clamp.** The clamp bounds the disk at the frame diagonal and is *lossless*, but it **converts a hang into a plausible-looking result**: a radius cell of `1e300` now samples the whole frame and reports success, so a unit error or a misread column yields believable output rather than an obvious failure. Note the load-time guard cannot cover it — `1e300` is a positive finite number and passes `parseRadius` unchanged — so the only place that can see it is the sampler, and the only place that can *report* it per detection is `ZExtractor`, where `sampleStatus` already lives. Deferred because it needs two decisions, not because it is unwanted: which status to use (reusing `STATUS_OUT_OF_BOUNDS` would misattribute, as the NaN-radius case did before p10.13), and whether a clamped radius is a per-detection fault at all when the radius is a per-*row* property. See [Reading the radius column or sizing the sampling disk](GOTCHAS.md#reading-the-radius-column-or-sizing-the-sampling-disk) for the clamp itself and why it must not become a refusal.

- **`zStd` cannot distinguish one valid sample from many ("finding #4").** `ZAggregator.std` returns `0.0` for fewer than two valid values, so a `RADIUS` detection clipped to a single pixel at an image edge — or one where 19 of 20 sampled pixels were unmapped/NaN — reports `zStd = 0.0`, reading as maximal confidence. **`zStd` is the wrong place to carry that signal**, and p10.12's end-to-end trace is the evidence: `0.0` also arises *legitimately* when every valid sample resolves to the same index, so the value is not distinguishable from a genuine zero spread by any rule. The likely answer is surfacing the **valid-sample count** beside the Z (`numSamples` minus `numUnmapped`), which is a design decision about what the outputs should contain rather than a fix to apply. **Severity is currently low and that is load-bearing:** `zStd` is computed in both extractors and stored on `ExtractionResult`, but is read by **nothing** — no exporter, no log line, no dialog, no `.npy` column (3-D is `[X,Y,Z,T]`), no Results Table column (`Track_ID,Frame,X,Y,Z`), no ROI field. Its only consumer anywhere is `ExtractorEquivalenceTest`. So a misleading `0.0` is presently invisible to users; **if `zStd` is ever surfaced, this becomes a real confidence number someone could act on, and must be resolved first.**

- **`ZMappingLoader` key overflow.** The key is read with `Integer.parseInt` on the `\d+` capture, so an absurdly long digit run throws an uncaught `NumberFormatException` rather than a clear message. Also noted in [Parsing the Z-mapping JSON](GOTCHAS.md#parsing-the-z-mapping-json). Its own patch.

- **Four `processDataset` behaviours are untestable without widening two visibilities.** *(Moved here verbatim from `CLAUDE.md`'s test-suite prose at p10.23, where it had been filed among descriptions of what the suite covers rather than among decisions. Re-verified against the code before the move: `processDataset` is still `private` at `ZProjectorPlugin:465`, `Config`'s constructor is still package-private at `ZProjectorDialog:61`, the return is still `total - written` at `:617`, `written++` still sits after the skip's `continue`, and the dimension check still precedes the bit-depth NOTE. No test constructs `Config` or reaches `processDataset`.)* **Deliberately NOT covered — four specific unverified behaviours, all of them p10.6's exact failure mode:** (1) a dimension-skipped timepoint counts into the `total - written` return; (2) it therefore reaches the run-summary `WARNING` about skipped timepoints; (3) it does not increment `written`, so it never contributes to a "success"; (4) the dimension check runs *before* the bit-depth NOTE, so a skipped timepoint neither emits a NOTE nor becomes `previousBitDepth`. None of these is asserted anywhere. They are unreachable from a test because `processDataset` is `private` **and** `ZProjectorDialog.Config`'s constructor is package-private in `ztracker.ui.projector` — covering them needs *both* widened, which was judged a worse trade than this documented gap. The pure helpers were split out precisely so the *decisions* are tested even though the loop around them is not; **the only thing that exercises these four is a manual Fiji run**, so re-verify them by hand when changing this loop.
- **`ProjectionStackScanner.openStack`'s in-memory fallback silently forfeits streaming, and its multi-slice compressed case is untested.** `openStack` opens the timepoint virtually where it can and otherwise falls back to `IJ.openImage`, which reads the **whole file into memory** — precisely what the streaming design exists to avoid (see [Refactoring how the TIFF-stack input reads slices](GOTCHAS.md#refactoring-how-the-tiff-stack-input-reads-slices)). Four conditions send it down that path, all inside `tryOpenVirtual`: the TIFF is **not a contiguous ImageJ stack** (`info == null || info.length != 1`, i.e. multi-IFD), it holds a **single image** (`nImages <= 1`), its pixels are **compressed** (`compression > COMPRESSION_NONE`), or reading the header **throws anything at all** (the blanket `catch (Throwable)`). **What is actually covered today:** `tryOpenVirtual_returnsNullForSingleImageTiff_soTheNormalOpenHandlesIt` pins the single-image null return; `scanDataset_throwsOnSingleSliceFile_pointingAtTheOtherInputType` runs the fallback branch end to end, since a 1-slice file really does fall through to `IJ.openImage` before `scanDataset` rejects it; and `virtualAndInMemoryReads_agreeOnLabelsAndPixels` proves the two read routes see identical labels and pixels — but on an **uncompressed** stack, calling `IJ.openImage` directly rather than through `openStack`. **No test writes a compressed TIFF anywhere in the repo**, so the one case where the fallback would pull hundreds of MB into the heap — a multi-slice *compressed* stack — is unexercised. **And the forfeit is silent:** nothing logs that a file could not be streamed and is being loaded whole, so the only symptoms are memory and time. **Be exact about what "untested" means here**, since README's "Memory and large datasets" section states this path's cost and the two should not read as one of them being stale: what is unverified is **correctness on a compressed file** — above all whether the **slice labels survive the decode**, since every Z depth is parsed from them and a lost label fails the whole dataset. The fallback *branch* is exercised (by the single-slice test named above), and the memory *cost* is arithmetic and is documented for users in that README section — neither of those is the gap.
  **Why it is left alone — no known producer.** The acquisition software writes **uncompressed** TIFFs, and that is a property of the **writer, not of any one file**: stack dimensions vary between acquisitions, but whether the software emits compressed pixels does not, so the conclusion does not rest on a particular stack's size. The evidence is a real timepoint's Show Info — 1051 × 1674 × 401, 8-bit, reported **673 MB** — against `1051 × 1674 × 401 = 705,508,974 B`, which is that same 673 MB in Fiji's units (705,508,974 / 1024² = 672.8 MiB). Every pixel is stored raw with nothing but header overhead beyond it, so that file takes the streaming path and so will its siblings. **The ten-second check on any other file:** compare the reported size against `width × height × depth` bytes for 8-bit (double it for 16-bit, quadruple for 32-bit); a file meaningfully *smaller* than that product is compressed. This is the same bar already applied to `parseZLabel`'s two parse tolerances and the ignored-sub-folder case — a coherent hazard with no evidence of anything producing it.
  **What would change the decision:** compressed stacks entering the acquisition pipeline (a new microscope, new acquisition software, or a batch job run to shrink a dataset on disk), or a user reporting an unexplained out-of-memory or slowdown on **one** dataset while others of similar size are fine — that asymmetry is what a per-file fallback looks like from the outside.
  **The cheap fix, recorded so it is not re-derived:** one `IJ.log` line in `openStack` when `tryOpenVirtual` returns null on a **multi-slice** file, saying plainly that it could not be streamed and is being loaded whole. That converts the silent case into a visible one for the cost of a line and needs no fixture of its own. *Guarding* it — refusing such files, or decompressing slice-by-slice — is a much larger change and is **not** what is being deferred here.

- **A Z-layer folder name is parsed by `Double.parseDouble`, so the accepted set is whatever Java accepts — including forms nobody would type.** `ProjectionInputScanner.parseZ` is `Double.parseDouble(folderName.trim())` with `NumberFormatException` → `null`, so the rule is not "a plain number" but "a Java floating-point literal, and nothing else". Measured, not inferred: `-300`, `+300`, `-300.5`, `1e2` → 100, `-3E-2` → −0.03 are accepted, and so are **`300d`**, **`300f`** (Java's trailing type suffixes), **`0x1p3`** → 8 (hex float), **`NaN`**, **`Infinity`** and **`-Infinity`**. Rejected: `z-300`, `-300um`, `1,5` (decimal comma), `--300`, `1 000`, and the empty name. **The consequence worth naming** is `NaN`: a folder called `NaN` is accepted as a **real Z layer**, and `layers.sort(Comparator.comparingDouble(...))` places NaN **last** — verified, sorting `[NaN, -300, 0, Infinity, -Infinity, 5]` yields `[-Infinity, -300, 0, 5, Infinity, NaN]` — so it would be taken as the **deepest** layer, get the highest global index, and appear in the JSON mapping with a `NaN` depth that `ZMappingLoader` cannot match (its key pattern is digits-only, and the *value* would be unparseable text). **Why this is declined rather than deferred.** The fix is a production change under `src/main`, so it moves `<patch.version>` and requires a manual Fiji run — the full cost of a code patch to guard against a folder name no user will type, on a layout where the names come from acquisition depths. **And the obvious tightening is worse than the gap.** A regex like `-?\d+(\.\d+)?` would reject `1e2` and `-3E-2`, which are accepted today, are legitimate ways to write a depth, and would be silently dropped as non-layers — trading a hypothetical wrong answer for a real one, in the direction the ignored-sub-folder note already warns about (a dropped layer never competes in the projection, so a pixel whose true extremum lay in it is attributed to a surviving layer instead). Any tightening would have to enumerate the exotica to exclude rather than enumerate the numbers to accept, which is more code guarding less. **What would change the answer:** a real dataset arriving with a folder name in any of these forms, or a producer that writes depths programmatically in a locale or format that emits one — at which point the entry moves to `docs/BACKLOG.md`. Note the *silent* half is already covered: a sub-folder that fails to parse is reported by the ignored-sub-folder note, so the failure mode left open here is strictly the reverse — a name that parses when it should not.


- **The four TopoJ conversion parameters are user-declared rather than read from the file, because the only one that could be read cannot be trusted.** *(p11.0. Costed against reading `encodingScale` from `ij.measure.Calibration`, which is the obvious alternative and is not viable.)* **Verified here, not assumed:** ImageJ does not persist voxel depth for a **single-slice** TIFF, and Tool 3's input is exactly that — one single-slice file per frame (`TopoJStackLoader.readFrameInto` takes `imp.getProcessor()`; nothing in that loader traverses a stack). Measured against ij 1.54f: an `ImagePlus` saved through `FileSaver` carrying `pixelDepth = 2.0` and `pixelWidth = 0.5` reads back with **`pixelDepth == 1.0`** and `pixelWidth == 0.5` — the XY calibration survives and the Z calibration is dropped — while the identical calibration on a **3-slice** stack reads back `pixelDepth == 2.0`. Independently confirmed on real data: a height map produced from a correctly calibrated stack (`pixelDepth 2`, values running to 800) still reports voxel depth 1.0 under Image > Properties. **So the header cannot distinguish "no depth recorded" from "a genuine depth of 1.0"** — and 1.0 is precisely the common uncalibrated case — meaning a check built on it would pass while verifying nothing, which is worse than having no check at all, because it would read as one.

  **What replaces it** is the lattice and range test in `TopoJZConversion`, which validates the *declared* `encodingScale` against the pixel data itself. It catches a wrong scale in **both directions but by different mechanisms**: too **large**, and `v / encodingScale` stops being an integer, so the **lattice** test rejects it; too **small**, and the quotient runs past `nSlices - 1`, so the **range** test rejects it. **How loudly:** declaring `encodingScale 2` on the uncalibrated reference dataset fails on **307,911,939 of 636,893,388 pixels — 48.35%** — first offender `385.0 / 2.0 = 192.5`. That figure is exactly the number of odd values other than the sentinel, computed independently from a full-dataset histogram taken before the decoder existed (odd values excluding `1.0`: 307,911,939 = 48.346%; including it, 325,293,460 = 51.075%), and is consistent with the ~48.85% odd fraction measured separately on a single frame. **A wrong scale therefore fails on roughly half of every image, not on some rare edge case** — it fires on the first frame rather than deep into a run.

  **What none of it catches is `zStep`.** Nothing in the file records the true slice spacing, and no arithmetic over the pixels can recover it, since the lattice is built from `encodingScale` alone. `zStep` is therefore taken **on trust**, and a wrong one rescales every depth with nothing to notice; `zFirst` is the same, shifting them. That residual risk is what Step 2's on-screen wording spends its words on, separating the two scale-like inputs.

  **The measurement all of this rests on**, recorded because it exists nowhere else in the repo. Two TopoJ height maps of the **same acquisition timepoint**, one produced from an **uncalibrated** source stack (`pixelDepth 1`) and one from that same stack **recalibrated to 2**: of **1,759,374** pixels — 1051 x 1674, this dataset's exact frame size — the **1,589,113** whose uncalibrated value was not `1.0` satisfied `v_cal == 2 x v_uncal` **exactly, with zero mismatches**. Of the **170,261** pixels holding `1.0` in the uncalibrated map, **167,636 stayed 1** (the unassigned sentinel, which TopoJ never scales by pixelDepth) and **2,625 became 2** — genuine `k = nSlices-1` pixels whose value had been colliding with that sentinel. The arithmetic closes both ways: 1,589,113 + 170,261 = 1,759,374, and 167,636 + 2,625 = 170,261. **Everything else in this repo's record is inference from that comparison** — the encoding formula, the claim that the sentinel is unscaled, the ambiguity rule, and every number in p11.0's changelog row are its consequences. **Provenance, which matters more than the numbers:** it was performed outside this repo and reported into it; it was **not** re-run here, and neither height map is in the repo. Reproducing it as a test would need both maps committed as fixtures (~13 MB) against a repo that deliberately holds exactly one binary fixture.

  **What would change the answer:** ImageJ persisting voxel depth for single-slice TIFFs, or TopoJ recording the `pixelDepth` it used anywhere in its output — either would make the declared value checkable rather than merely constrained. A TopoJ version with a different initialisation literal or loop bound would instead **date** the measurement above rather than falsify it, and would need a fresh pair of maps.

- **The `k = 0` clamp puts a hard floor into aggregated Z, and on an unambiguous scale nothing excludes it from a median.** Observed during p11.0's manual Fiji run and recorded as behaviour, not as a defect. When `1.0` is **unambiguous**, `TopoJZConversion.toZ` converts the unassigned sentinel to `zFirst`, which is right for a single pixel: `k = 0` is exactly what TopoJ means, and `zFirst` is that slice's depth. But such a pixel means the surface sits **at or above** the top of the acquired range, so `zFirst` is a **floor, not a measurement** — the true depth is unknown and lies somewhere above it. On the recalibrated version of the motivating dataset that is **15,648,128 pixels, 2.46% of 636,893,388**, each carrying a hard `-400` µm, and `ZAggregator` cannot tell them from measured depths: a `RADIUS` disk straddling that boundary takes a median over real depths and floors together, and reports it with the same confidence as any other. **The consequence is counter-intuitive and worth stating plainly: on this axis the *ambiguous* path behaves better.** There the same pixels become `NaN`, and `ZAggregator.filterNaN` removes them before aggregating, so a partly-clamped footprint aggregates over its real samples only — the ambiguity that costs those pixels entirely also keeps them from contaminating their neighbours. **Not a defect, and not scheduled:** the clamp is deliberate, is documented at `TopoJZConversion.toZ`, and is provably correct for a single pixel; the interaction appears only once several pixels are combined, which is a different question from the one the clamp answers. **What would change the answer:** deciding that "at or above the top of the range" should be its own outcome rather than a depth — most likely a distinct status, or exclusion from aggregation — at which point this moves to `docs/BACKLOG.md`.

- **The menu label "3D Z-Extractor (TopoJ / direct-Z)" keeps the words "direct-Z", although p11.0 made them arguable.** *(Costed and declined at p11.1, when the surrounding documentation was corrected. Recorded so it is not re-proposed as pending work.)* Since p11.0 a TopoJ pixel is decoded rather than read as a depth, so "direct-Z" no longer describes the arithmetic. It still describes the thing users actually choose between: Tool 3 derives Z **directly from the pixel values**, with no JSON mapping file to supply, which is exactly what separates it from Tool 2 at the moment of picking a menu item. **The label is navigation, not documentation.** It is how the tool is found in `Plugins > ZTracker`, how colleagues refer to it in conversation, and what `plugins.config` registers; renaming it would ripple into `README.md`, `CLAUDE.md`, the user guide and several javadocs, and would strand every existing reference — for a phrase that is defensible on the reading that matters at the menu. The precise mechanism is explained where a user meets it, in the guide's Part 2 and in Step 1's on-screen description, both of which now say the pixel holds an encoded slice counter. **What would change the answer:** a second TopoJ-style tool that also decodes, which would make "direct-Z" ambiguous rather than merely loose; or user evidence that the label itself is what led someone to skip Step 2's parameters as optional.
